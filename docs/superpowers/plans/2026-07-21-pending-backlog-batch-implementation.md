# 잔여 백로그 일괄 구현 계획

> 대상 설계: `docs/superpowers/specs/2026-07-21-pending-backlog-batch-design.md`

목표는 HD-BL-007~011을 구현하고 기존 플레이 흐름을 회귀 검증한 뒤 GitHub Pages에 배포하는 것이다. 정책 숫자에는 신규 전용 테스트를 추가하지 않고 기존 기대값만 갱신한다.

## 작업 1: 오프리시 연속 이동 회귀 테스트

파일:

- 수정: `tests/unit/EnemySystem.test.ts`

절차:

1. 오프리시 보호자를 4초 이상 고정 스텝으로 이동시킨다.
2. 매 스텝의 경로 진행도 증가량이 `speed * dt`를 넘지 않는다고 검증한다.
3. 현재 구현에서 4초 경계의 64만큼 도약 때문에 실패함을 확인한다.

## 작업 2: 오프리시 대시 제거

파일:

- 수정: `src/game/enemies/EnemySystem.ts`
- 수정: `tests/unit/EnemySystem.test.ts`

절차:

1. 대시 거리·주기 상수와 경계 분할을 제거한다.
2. 감속 경계의 결정론은 유지한다.
3. 대시 잔여 스냅샷 값은 호환이 필요하면 0으로 유지한다.
4. ETA 계산을 연속 이동 속도만 사용하도록 맞춘다.
5. 기존 대시 전용 테스트를 연속 이동 기대값으로 바꾼다.
6. EnemySystem 테스트를 통과시킨다.

## 작업 3: 꼬리 마지막 프레임 회귀 테스트

파일:

- 수정: `tests/unit/PlayerViewImpactAction.test.ts`

절차:

1. 꼬리치기 애니메이션의 마지막 프레임 시작 시각을 계산한다.
2. 종료 직전까지 마지막 프레임이 유지되고 전체 유지 구간이 800ms인지 검증한다.
3. 현재 500ms 몸동작 상수로 실패함을 확인한다.

## 작업 4: 꼬리치기 시각 효과와 몸동작 수정

파일:

- 수정: `src/game/player/PlayerView.ts`
- 수정: `src/game/scenes/GameScene.ts`
- 수정: `src/game/combat/CombatEffectPool.ts`
- 수정: `tests/unit/CombatEffectPool.test.ts`
- 수정: 관련 GameScene 단위 테스트

절차:

1. PlayerView에서 마지막 프레임 800ms 유지가 포함된 전체 동작 시간을 내보낸다.
2. GameScene이 해당 시간을 몸동작 종료 기준으로 사용하게 한다.
3. 꼬리치기 적중 시 원형 호·원형 먼지를 생성하는 경로를 제거한다.
4. 전투 이펙트 풀의 사용되지 않는 꼬리 타입과 렌더러를 정리한다.
5. 기존 테스트를 새 의도에 맞게 갱신하고 관련 테스트를 통과시킨다.

## 작업 5: 정책값 반영

파일:

- 수정: `src/game/data/balance.ts`
- 수정: `src/game/enemies/EnemyActor.ts`
- 수정: `src/game/enemies/DogTraderRig.ts`
- 수정: `src/game/skills/skillDefinitions.ts`
- 수정: `src/game/skills/SkillSystem.ts`
- 수정: 관련 기존 단위 테스트

절차:

1. 두 보스 속도를 1.2배로 변경한다.
2. 공용 보스 애니메이션 배율을 일반 액터와 트럭 리그에 적용한다.
3. 꼬리치기와 안전신문고 일반 쿨타임을 각각 6000ms와 19000ms로 변경한다.
4. SkillSystem에 첫 1000ms 쿨타임 창을 도입한다.
5. 첫 성공 시전 뒤 일반 쿨타임 창으로 전환한다.
6. 기존 테스트의 정책 기대값만 갱신한다.

## 작업 6: 안전신문고 비용 일원화

파일:

- 수정: `src/game/progression/ProgressionSystem.ts`
- 수정: `src/game/ui/SkillDock.ts` 또는 실제 하단 독 구현 파일
- 수정: 관련 타입과 기존 테스트
- 수정: 필요 시 테스트 시나리오의 간식 지급량

절차:

1. 현재 구매 단계 기본 비용과 스킬 ID를 받아 실제 비용을 반환하는 공용 함수를 만든다.
2. 안전신문고에만 5를 더해 20/30/45가 되게 한다.
3. 구매 큐 검증과 실제 차감에 공용 함수를 사용한다.
4. 하단 독의 비용·구매 가능 상태에도 같은 함수를 사용한다.
5. 기존 테스트와 시나리오 기대값을 갱신한다.

절차:

1. 변경을 논리 단위로 검토하고 민감정보가 없는지 확인한다.
2. 설계/계획, 동작 수정, 정책 변경을 이해 가능한 커밋 단위로 만든다.
3. 현재 브랜치를 원격에 푸시한다.
4. Pages가 배포하는 기본 브랜치에 필요한 방식으로 반영한다.
5. GitHub Actions 워크플로 성공을 확인한다.
6. 공개 Pages URL의 상태 코드와 핵심 정적 자산 응답을 확인한다.
